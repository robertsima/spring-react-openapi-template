# 01 - Why Contract-First in Modernization Projects

## The short answer

Code-first works well when one team owns both ends of an API and ships them together. Modernization
projects are almost never like that. A legacy system is being taken apart, several teams build the
replacements in parallel, and the old system often keeps running alongside the new one for months.

Under those conditions the API is the main thing teams agree on. Code-first leaves that agreement
implicit until a controller exists. Contract-first makes it explicit before anyone builds on it. The
extra cost is writing YAML before Java. What you save is integration rework, which is usually the most
expensive kind on the program.

The rest of this doc supports that claim, then covers where it doesn't hold.

## What "contract-first" means here

| | Code-first | Contract-first (this template) |
| --- | --- | --- |
| Source of truth | Java controllers and DTOs | `openapi/openapi.yaml` |
| The spec is | generated from code (e.g. springdoc), after the fact | written and reviewed before code |
| Frontend types | hand-written, or generated from a running backend | generated from the same file at build time |
| A breaking change shows up | at integration or in production | as a compile error, or in review of a one-file diff |
| Who can start work | consumers wait for the provider's code | both sides start from the agreed contract |

Code-first teams often have an OpenAPI document too, generated by springdoc. That document only
describes what was built. Nobody agreed to it beforehand, and nothing forces the next build to match it.

## Root cause: why integration breaks (5 Whys)

A typical failure on a modernization program, traced back:

1. **Why did the release slip?** The new orders UI and the new orders service didn't work together in
   the integration environment.
2. **Why not?** The UI sent `customerId` as a string and expected `totalAmount` in cents. The service
   took a number and returned a decimal.
3. **Why did each team assume something different?** Each built against its own reading of the legacy
   screen and a wiki page. The real interface only existed once the service code was written.
4. **Why was the interface only in code?** The process was code-first. The provider team owned the
   shape of the API, and nobody reviewed it as a separate thing.
5. **Why does that matter more here than on a normal project?** The teams work in parallel against a
   moving legacy target, so a wrong guess stays hidden for weeks, not hours.

**Root cause:** the interface was a by-product of implementation instead of an agreed input to it.
Contract-first fixes the cause, not just this one symptom.

## What you get (Pyramid: supporting points)

### 1. Teams stop waiting on each other

When the contract is merged, the frontend generates its client and can build against a mock (this
template's frontend integration tests do that with MSW). The backend generates its interfaces and
implements them. Neither side needs the other's code to make progress.

### 2. Drift becomes a compile error

The backend controller `implements` a generated interface. If someone renames a field in the spec, the
backend no longer compiles until the code matches. The TypeScript client changes the same way, so the
UI breaks at build time instead of at runtime. A mismatch can't reach the integration environment
without someone ignoring a red build.

### 3. API review happens before anyone builds on it

A change to the contract is a small YAML diff that architects, consumers and security can read without
understanding the implementation. Reviewing an API inside a 40-file controller PR is much harder, and
by then two teams may already depend on it.

### 4. The legacy system gets a target, not a copy

Modernization tends to reproduce legacy quirks, because the fastest code-first path is to mirror the old
tables or screens. Writing the contract first makes you decide what the new interface should be, and
lets an anti-corruption layer translate the legacy data underneath it.

### 5. One description serves many consumers

The same file produces server stubs, the TypeScript client, Swagger UI and mock servers. It can also
drive contract tests and API-gateway configuration. On a program with many consumers, that keeps one
definition in charge instead of five hand-maintained ones.

## Honest assessment (SWOT)

### Strengths

- Interface disagreements surface in review, before code depends on them.
- Parallel work: consumers and providers start from the same merged contract.
- Generated types on both sides remove a whole class of serialization and naming bugs.
- The contract is readable by non-Java and non-TypeScript reviewers.

### Weaknesses

- An upfront step: someone has to write YAML before writing code, and that feels slow at first.
- Generators have opinions. Some OpenAPI constructs (`oneOf` with discriminators, complex
  inheritance) generate awkward code, and you may adjust the spec to suit them.
- Generator versions must stay in sync across backend and frontend (this template pins them in three
  places, listed in the root README).
- Developers who are used to annotations-first may resist at first.

### Opportunities

- Contract tests and mock servers come almost for free once the spec exists.
- The same spec can configure API gateways, client SDKs for other teams, and documentation portals.
- Contracts can be versioned and reviewed like any other architecture artifact, which helps governance on
  regulated programs.

### Threats

- **Spec rot:** if people edit generated code or add hand-written endpoints outside the contract, the
  benefit erodes. Generated code is git-ignored in this template so it can't be edited by accident.
- **Big-bang specs:** trying to design every endpoint upfront recreates waterfall. Write the contract
  one endpoint or one slice at a time, just ahead of implementation.
- **Ownership gaps:** if no one is accountable for the contract, reviews get skipped. See the RACI in
  [03 - Day-to-day workflow](03-workflow.md).

## Common objections

**"springdoc already gives us a spec from code."**
It gives you a description of what was built. Contract-first gives you an agreement before it's built,
plus a build that fails when the code stops matching. In a single-team service the difference is small.
Across teams it is the whole point.

**"Writing YAML is slower than writing a controller."**
For one endpoint, yes, by minutes. The YAML replaces the hand-written DTOs and client code on both
sides, which are generated. The real comparison is minutes of YAML against days of integration
debugging.

**"Our API will change as we learn."**
That's expected. Contract-first doesn't freeze the API. It makes every change visible and reviewable,
and the compiler shows everything a change affects.

**"We're replacing a legacy system screen by screen, the interfaces are obvious."**
They're obvious to each team separately. The 5 Whys example above is what happens when two teams find
the same thing obvious in different ways.

## When code-first is fine

- A single team owns the service and its only client, and they ship together.
- Throwaway prototypes and spikes.
- Internal admin endpoints that no other team will call.

Even then, this template still works. You just edit the spec and the controller in the same PR.
